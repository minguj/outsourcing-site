# 운영 플랫폼(PMS) 데모

API: `/api/demo/pms/*` · 화면: `/demo/pms` (검색 제외, 공개 화면 미링크)

시니어하우징·임대주택처럼 **소유주가 다른 여러 사업장을 위탁 운영**하는 상황을 가정한 운영 플랫폼 샘플.
공개된 채용 공고의 범위(고객·사업장·호실·계약·청구·수납, Multi-site, 역할별 권한, 개인정보 보호)를 바탕으로
첫 버전(MVP)을 어떻게 설계할지 보여 주는 개인 샘플이다. 운영사·소유주·사업장·사람은 모두 가상이다.

## 구조
```
backend/pms/
  billing.py   청구·수납 계산 (I/O 없음): 일할 계산, 서비스 이용료, 납부 기한, 연체료, 청구서 상태
  access.py    역할 × 사업장 권한 (I/O 없음): 역할별 권한, 사업장 범위, 연락처 가림, 건강정보 열람 제한
  voc.py       민원 분류 규칙 (I/O 없음): 분류·긴급도·담당 역할, 개인정보 가리기, 키워드 대체 분류, AI 응답 검증
  voc_ai.py    민원 분류용 Claude 호출 (가린 문장만, 도구 호출로 정해진 값만 받음)
  integration.py 출입 시스템 연동 (I/O 없음): 이벤트, HMAC 서명, Idempotency-Key, 재시도·실패 처리, 가상 출입 시스템
  ledger.py    회계 분개 (I/O 없음): 청구·수납 → 분개, 차대 검증, CSV
  service.py   업무 규칙: 호실 현황, 입주자 조회(감사 기록), 서비스 이용 기록, 계약 상태 흐름, 월 청구 실행, 수납,
               민원 접수·처리, 연동 이벤트 발행·처리, 회계 내보내기·월 마감
  seed.py      가상 샘플 데이터 (사업장 2곳, 호실 20개, 입주자 7명, 체험 사용자 6명, 샘플 민원 4건, 연동 이벤트)
  router.py    API (입출력 변환, 샌드박스)
backend/tests/test_pms_demo.py
```

## 데이터 모델
```
운영사 ─ 소유주 ─ 사업장(자산 유형, 요금표, 납부일·연체 이율) ─ 동·층 ─ 호실(정비 여부)
입주자 ─ 보호자 / 건강·돌봄 정보(별도 열람 권한)
계약: 호실·입주자·기간·보증금·월 이용료·상태
청구서: 계약 × 월 (한 번만 생성), 청구 항목(월 이용료 + 서비스 이용료)
수납: 청구서별 부분 납부
서비스 이용: 입주자·서비스·수량·날짜 (사업장 요금표에 있는 서비스만)
감사 기록: 누가 언제 어떤 입주자의 민감 항목을 원문으로 봤는지
민원: 입주자·원문/가린 문장·분류·긴급도·요약·근거·출처(ai|rule|sample)·담당 역할·상태
연동 이벤트(아웃박스): 종류·Idempotency-Key·본문·적용일·상태·시도 기록 / 출입카드 상태(가상 출입 시스템)
월 마감: 사업장 × 월, 마감 시각·마감자
```
운영 데이터에는 모두 `site_id`가 있고, 모든 조회는 서버에서 사용자 범위로 거른다.
공통 구조는 같고 사업장별로 요금표·납부일·연체 이율만 다르게 둬서, 자산 유형이 달라도 같은 코드로 동작한다.

## 역할과 권한
| 역할 | 사업장 범위 | 주요 권한 |
|---|---|---|
| 본사 관리자 | 전체 | 사업장·계약·청구 조회, 연락처 열람, 감사 기록 (청구 실행·건강정보는 불가) |
| 사업장 매니저 | 배정 사업장 | 계약 상태 변경, 월 청구 실행, 수납, 연락처·건강정보 열람, 감사 기록 |
| 현장 케어 직원 | 배정 사업장 | 건강·돌봄 정보 열람, 서비스 이용 기록 (연락처는 가림, 계약·청구 불가) |
| 회계 담당 | 배정 사업장 | 계약 조회, 월 청구 실행, 수납, 연락처 열람 (건강정보 불가) |
| 보호자 | 본인 가족 | 가족의 청구서·기본 정보 조회, 가족 민원 접수·조회 |

3단계 권한 (민원 범위는 `voc_scope`로 한 번 더 좁힌다)
| 역할 | 민원 | 출입 연동 | 회계 |
|---|---|---|---|
| 본사 관리자 | 전체 조회 | 조회 | 내보내기·월 마감 |
| 사업장 매니저 | 전체 조회·접수·처리 | 조회·처리 | - |
| 현장 케어 직원 | 케어 직원에게 배정된 것만 조회·접수·처리 | - | - |
| 회계 담당 | 회계에 배정된 것만 조회·처리 | - | 내보내기·월 마감 |
| 보호자 | 내 가족 것만 조회·접수 | - | - |

- 범위 밖 데이터는 403이 아니라 404로 응답해 존재 여부도 드러내지 않는다.
- 연락처·건강정보를 원문으로 보여 주면 감사 기록에 남긴다.

## 계약 상태
`작성 중 → 체결 → 입주 → 해지`, `작성 중/체결 → 취소`
- 정비 중인 호실, 같은 호실에 진행 중인 다른 계약이 있으면 체결·입주할 수 없다.
- 해지 시 퇴거일을 기록한다. 퇴거일 전까지는 호실이 '입주'로 보인다.

## 청구 규칙 (사업장 요금표로 바꿀 수 있는 가정)
- 월 이용료는 그 달에 계약이 유효한 날수만큼 일할 계산 (입주일·퇴거일 포함), 10원 미만 버림.
- 서비스 이용료 = 그 달 이용 수량 × 사업장 단가.
- 납부 기한 = 다음 달 사업장 납부일 (말일보다 크면 말일).
- 연체료 = 남은 원금 × 연 이율 × 연체 일수 / 365 (단리, 10원 미만 버림).
- 같은 계약·같은 달 청구는 다시 실행해도 한 번만 만든다.
- 테스트 기대값은 손으로 계산했다 (엔진 출력을 복사하지 않는다).

## 샌드박스
- `POST /sandbox`로 방문자마다 가상 데이터 사본을 메모리에 만든다. 2시간 뒤 지우고 DB에 남기지 않는다(최대 300개, IP당 시간당 30개).
- 이후 요청은 `X-Pms-Sandbox`(토큰)와 `X-Pms-User`(체험 사용자 id) 헤더로 보낸다. 사용자 id를 바꾸면 역할이 바뀐다.
- 실제 개인정보를 받거나 저장하지 않는다.

## 민원(VOC) AI 분류
- 접수 → 이름(입주자·보호자·직원)·전화번호·이메일을 가림 → Claude에 가린 문장만 보냄 → 도구 호출(`classify_voc`)로
  분류(시설/소음·생활/요금·계약/돌봄·건강/기타)·긴급도·한 줄 요약·근거를 받음 → 정해진 값인지 검증 → 담당 역할 배정.
- AI를 못 쓰면(키 없음, 호출 실패, 형식 불일치, 사용량 초과) 키워드 규칙으로 분류하고 출처를 `rule`로 남긴다.
- 사용량 상한: 체험 1회당 10건, 서버 전체 시간당 200건, IP당 시간당 접수 20건. 모델은 `PMS_VOC_MODEL`(기본 claude-haiku-5-5).
- 연락처 원문 권한이 없는 역할(케어 직원)에게는 가린 문장을 보여 준다.
- 상태: 접수 → 처리 중 → 완료.

## 출입 시스템 연동 (가상)
- 계약이 입주로 바뀌면 입주일에 `access.grant`, 해지되면 퇴거일에 `access.revoke` 이벤트를 아웃박스에 쌓고 적용일이 되면 보낸다.
- 본문은 정렬한 JSON, 헤더 `X-Signature: sha256=HMAC(비밀키, "타임스탬프." + 본문)`, `X-Timestamp`, `Idempotency-Key`(계약·종류마다 하나).
  비밀키는 체험마다 새로 만들어 메모리에만 둔다.
- 받는 쪽은 서명을 확인하고, 이미 처리한 키는 처리하지 않고 200으로 답한다.
- 실패하면 1분·5분·30분 뒤 다시 보내고 4번째도 실패하면 `dead`(수동 확인). 데모의 '처리' 버튼은 대기 시간을 건너뛴다.

## 회계 내보내기·월 마감
- 청구: 말일자 (차) 매출채권 / (대) 이용료수익·서비스수익. 수납: 받은 날짜 (차) 보통예금 / (대) 매출채권.
- 연체료는 계산만 하고 아직 청구하지 않으므로 분개하지 않는다.
- 차대 합계가 같아야 CSV(엑셀용 BOM)로 내보내고 마감할 수 있다.
- 마감한 달은 월 청구 실행, 그 달 날짜의 수납·서비스 이용 기록을 막는다.
