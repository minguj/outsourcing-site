# 거래처 발주서 자동 변환·검수 데모

경로는 `/demo/purchase-orders`다. 첫 버전은 제공된 가상 A/B/C XLSX만 지원한다. 파일 업로드, AI, DB, 실제 고객 데이터는 사용하지 않는다. 샘플 생성·expected와 별도로 backend가 실제 XLSX/CSV를 읽어 계산한다. expected JSON은 테스트에서만 사용한다.

## 데모의 목적과 검수 UI

핵심 메시지는 **거래처마다 다른 발주서를 우리 회사의 동일한 거래명세서 양식으로**다. 상단의 실제 A/B/C 원본 썸네일에서 공통 양식으로 이어지는 구도로 표시한다. 거래처별 데이터를 한 문서로 섞는 것이 아니라, 각 거래처를 동일한 포맷의 별도 XLSX로 발행한다.

- 데스크톱: 오른쪽 결과에 더 넓은 공간을 배정한다. 원본은 접기·펼치기와 확대 대화상자를 제공한다. 확대 보기는 닫기 버튼이나 Escape로 닫는다.
- 결과의 9열은 다운로드와 같은 순서·용어인 순번, 품목코드, 표준품명, 단위, 수량, 단가, 공급가액, 부가세, 합계다.
- 확인 필요 행은 결과 표에 남는다. 수량·품목·금액 문제가 있는 셀을 강조하고, 아이콘과 텍스트 상태 배지로 구분한다. 별도 하단 오류 목록은 없다.
- 수량 적용·재검증, 마스터 선택, 계산 금액 확인, 사유 기록 후 제외를 같은 행에서 처리한다. 서버 응답으로 상태·금액·합계·남은 확인 건수를 바로 갱신한다.
- 전체/확인 필요/제외 필터는 표시할 행만 바꾼다. 합계는 필터와 관계없이 서버가 확정한 행만 포함한다. 미해결 상태의 합계는 부분 합계이며 최종 발행 금액이 아니다.
- 취합한 정상 행은 여러 원본을 한 결과 행으로 표시한다. 원본 행·셀 펼치기에서 B의 모든 원본을 확인한다. 취소·사유 제외 행도 전체/제외 필터에서 남겨 둔다.
- 정상 행은 한 줄로 표시하고 오류 행에만 필요한 입력과 설명을 펼친다. 납기·원본 추적은 기본적으로 접힌 행별 상세에 배치한다. 추적은 `원본 2·4·8행 / 수량 3+5+4=12`처럼 한국어로 표시한다. 수정 되돌리기는 원본 추적 펼침 안에서 제공한다.
- 모바일: 원본/공통 결과 탭으로 전환한다. 결과는 가로 스크롤 없는 카드로 품명·상태·수량·금액을 표시하며 오류 카드의 수정 버튼으로 입력을 펼친다. B 원본은 14px와 가로 스크롤을 유지한다. 다운로드 XLSX는 기존 공통 9열을 유지한다.

기존 서버 검증과 미해결 거래처의 발행 차단 규칙은 변경하지 않았다. 브라우저 검증은 A/B/C를 각각 내려받아 같은 9열과 서로 다른 거래처 정보를 확인한다.

## 로컬 실행

프로젝트 루트의 PowerShell 터미널 1에서 기존 Python 3.12 가상환경을 사용한다.

```powershell
.\backend\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --reload --reload-dir backend
```

터미널 2:

```powershell
cd frontend
npm.cmd run dev -- --hostname 127.0.0.1 --port 3000
```

브라우저에서 http://127.0.0.1:3000/demo/purchase-orders 를 연다. frontend의 개발 전용 rewrite가 `/api/*`를 localhost:8000으로 전달하므로 두 서버가 필요하다. 서로 다른 localhost/127.0.0.1 주소를 섞지 않는다. 기존 Next 설정은 보존했다. 프로덕션에서는 기존 Caddy가 API를 전달한다.

새 환경에서는 backend/requirements.txt와 frontend/package-lock.json의 기존 의존성을 먼저 설치한다. 이번 구현은 새 런타임 라이브러리를 추가하지 않았다.

## 최초 결과 (새 expected 기준)

| 샘플 | 주문 원본 | 확정 원본 | 검수 | 취소 | 출력 품목 | VAT 포함 부분 합계 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| A | 10 | 8 | 2 | 0 | 8 | 134,640원 |
| B | 18 | 13 | 2 | 3 | 6 | 121,550원 |
| C | 11 | 8 | 3 | 0 | 8 | 138,600원 |

합계는 원본 39행, 확정 원본 29행, 검수 7행, 취소 3행이다. 화면의 부분 합계는 미해결 행을 제외한 금액이며 최종 발행 금액이 아니다. 검수가 끝난 **거래처별로** 최종 다운로드를 허용한다. 다른 거래처의 오류는 이미 검수를 마친 거래처의 다운로드를 막지 않는다.

## 브라우저 확인 항목

1. A/B/C의 원본 보기를 선택한다. 실제 XLSX 셀·병합 정보가 표시되는지, 파일명·시트와 셀 주소를 확인한다. 원본 XLSX 링크도 제공한다.
2. 전체 체험으로 위 최초 결과를 확인한다. B 원본은 14px 글자와 가로 스크롤을 사용한다. 출력의 원본 추적을 열어 물티슈 원본 2·4·8행과 G2/G4/G8 등의 셀을 확인한다. 취소 5·11·17행은 취합에 포함되지 않는다.
3. A 15행 수량에 5를 입력하고 적용·재검증한다. A 19행은 원본 13,000원과 계산 13,500원을 비교한 뒤 체크하고 계산 금액으로 확정한다. A의 다운로드가 활성화되고 공급가액 144,900원, VAT 포함 159,390원이 된다.
4. B 9행 위생장갑에서 M 또는 L을 명시적으로 선택한다. L을 고르면 기준단가 8,500원으로 바뀌어 금액 확인이 다시 필요하다. 단가 8,000원이라는 이유로 M을 자동 선택하지 않는다.
5. B 13행 미등록 품목은 마스터에서 직접 선택하거나, `+ 신규 등록`으로 품목코드·표준품명·단위·기준단가를 입력해 신규 품목으로 등록하거나(품목코드는 영문·숫자·하이픈 2~10자, 기존 코드와 중복 불가. 비워 두면 '미정'으로 등록되어 화면·거래명세서에 미정으로 표시되고 신규등록품목 시트에 '코드 부여 필요'로 남는다), 세 글자 이상 사유를 적고 제외한다. 마스터를 선택·등록하면 표준명·단위·기준단가를 적용하므로 기재 금액과 달라지면 확인한다. 신규 품목은 해당 체험 세션의 마스터에만 추가되며 item_master.csv는 바뀌지 않는다(체험당 최대 20개). 다운로드 XLSX에는 해당 거래처에서 쓴 신규 품목이 `신규등록품목` 시트로 정리된다.
6. C의 품목명·규격 매칭, 2.75L 수량, 11·18행 구분행과 빈 행·합계행 제외를 확인한다. 출력 행의 2026-11-09/2026-11-12 납기가 유지되어야 한다.
7. B의 취소 5·11·17행은 `↺ 취소 철회`로 일반 주문처럼 다시 검수할 수 있다. 17행 청소물티슈는 S009 별칭이라 바로 물티슈 출력 행에 취합되고(12+10=22), 5행 위생장갑은 M/L 선택, 11행 가상 포장필름은 마스터 선택·신규 등록·사유 제외 흐름을 탄다. 철회한 행은 `취소 철회` 표시와 원본추적의 `검수 완료 · 취소 철회`로 구분된다. 수정 되돌리기는 검수 수정을 먼저 되돌리고, 철회만 남은 상태에서는 다시 취소 상태로 돌린다.
8. 미해결 상태에서는 다운로드가 비활성이다. 버튼을 우회해 API를 호출해도 409를 반환한다. 사유로 제외한 행은 화면과 다운로드의 원본추적에 남는다.
9. 별도 시크릿/브라우저 프로필에서 다른 체험을 시작해 상태가 섞이지 않는지 확인한다. 같은 브라우저의 탭은 쿠키를 공유하며, 다른 탭의 오래된 revision 변경 요청은 409로 거절한다.

## 서버 규칙과 다운로드

- A는 번호가 있는 품목행, B는 주문번호가 있는 주문행, C는 숫자 번호가 있는 주문행을 읽는다. 헤더는 실제 열 이름으로 찾는다.
- B의 취소/취소완료는 품목 매칭보다 먼저 제외한다. 판매상품번호는 내부 코드로 사용하지 않는다. 확정된 품목코드·단위·숫자 단가·납기가 같은 행만 취합한다.
- C는 품명+규격으로 매칭한다. 규격이 있는 C 행은 알려진 규격이 아니면 이름만으로 확정하지 않는다. C는 서로 다른 납기를 합치지 않고 원본 주문행을 유지한다.
- 수정할 때마다 서버에서 재계산하고, 다운로드 순간에도 미해결 행과 revision을 확인한다. 수량·품목을 변경하면 이전 금액 확인은 무효가 된다.
- 금액은 Decimal, 공급가액은 원본 행별 원 단위 ROUND_HALF_UP, VAT는 확정 출력 행별 10% ROUND_HALF_UP이다. B 취합의 공급가액은 원본별 반올림값을 합친다. Excel 재계산에서도 같은 값이 되도록 취합 행의 공급가액 수식을 SUM(ROUND(...), ...)로 저장한다.
- XLSX에는 실제 숫자와 수식 캐시를 저장한다. 거래명세서, 모든 주문 원본의 추적·수정/제외 기록, 납기별내역을 담는다. 레이아웃 행이 있는 파일은 비주문행기록도 포함한다. 취합 결과의 각 원본은 같은 출력 순번으로 연결된다.
- 사용자 입력은 XML의 텍스트로 기록하며 수식으로 실행하지 않는다. 출력 템플릿의 스타일과 기본 수식은 보존한다.

## 상태 격리·제한

세션은 HttpOnly/SameSite=Strict 임의 쿠키와 별도 CSRF 확인값을 사용한다. 30분 고정 만료, 동시 최대 64체험, 행별 변경 최대 30회이며 서버 메모리에만 저장한다. 새 체험을 시작하면 같은 브라우저의 기존 체험을 초기화한다. 서버 재시작 시 사라진다. 배포는 기존 단일 Uvicorn worker를 유지하며 여러 worker/여러 서버로 확장하려면 공유 세션 저장소가 별도로 필요하다.

실제 개인정보를 입력하지 않는다. 샘플 전용 양식/OOXML만 검증했으며 범용 Excel 변환기, 로그인 기반 개인 업무 보관, 장기 저장 서비스가 아니다. 원본 미리보기는 Excel 네이티브 인쇄 화면과 차이가 있다. 실제 Excel/LibreOffice의 렌더링 엔진 검사는 수행하지 않았다.

## 테스트

프로젝트 루트에서 실행한다.

```powershell
.\backend\.venv\Scripts\python.exe -m unittest discover -s backend/tests -v
python -m unittest discover -s dev/purchase_order_samples -p "test_*.py" -v
cd frontend
npm.cmd run lint
npm.cmd run build
```

API 테스트는 새 expected와 초기 행·금액·추적을 대조하고, 실제 XLSX 셀 변조에 따른 결과 변화, 조건별 취합 분리, 규격·납기, 세션/CSRF/revision, 발행 차단, 실제 다운로드 숫자·원본 추적·반올림 수식을 검증한다.

선택적으로 Edge/Chrome의 격리된 프로필을 `--headless --remote-debugging-address=127.0.0.1 --remote-debugging-port=9223 --user-data-dir=<별도 임시 프로필>`로 열고 로컬 데모 URL로 이동한 뒤 다음을 실행한다.

```powershell
.\backend\.venv\Scripts\python.exe dev/purchase_order_demo/check_browser.py
```

검증 스크립트는 브라우저 버튼·입력·체크·제외·다운로드를 실행하고 종료 시 테스트 브라우저를 닫는다. 기존 개인 브라우저 프로필에 연결하지 않는다. 결과는 artifacts/browser-report.json과 다운로드 예시에 저장한다. 현재 UI 캡처는 artifacts/desktop-current.png와 artifacts/mobile-current.png 두 장만 유지한다.

## 컨테이너 연결

실제 공개 샘플과 마스터를 backend 이미지에도 포함하기 위해 backend 빌드 컨텍스트만 저장소 루트로 바꾸고 Dockerfile 경로를 명시했다. 루트 .dockerignore는 backend 코드와 해당 XLSX/CSV만 허용한다. dev/expected, .env, 키 파일은 이미지에 넣지 않는다. frontend 빌드, GHCR 게시, smoke, deploy의 실행 조건과 runner는 유지했다.

로컬에서 Docker 빌드를 수행하려면 저장소 루트에서 `docker build -f backend/Dockerfile .`를 사용한다. 이 환경에는 Docker가 없어 이미지 빌드·Compose 통합 검증은 수행하지 않았다. 이번 작업에서 commit/push·SSH·배포는 수행하지 않았다.
